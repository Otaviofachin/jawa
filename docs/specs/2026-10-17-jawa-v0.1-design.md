# Jawa v0.1 — Especificação

> Limpeza de disco para quem programa no Linux, pelo terminal. Encontra o que as ferramentas de desenvolvimento acumulam, explica cada item e só apaga depois de várias verificações de segurança.

O nome vem dos Jawas de *Star Wars*, os catadores que percorrem o deserto recolhendo sucata.

## Origem e autoria

- Projeto **100% autoral**. Nenhuma linha de código do [Sam](https://github.com/Pedro-B-Siqueira/sam) (app de limpeza para macOS) entra aqui.
- O Sam é **referência de ideias**: explicar cada item antes de limpar e travar a limpeza aos itens que o próprio app mediu. Ele recebe crédito no README como inspiração.
- Quem implementa trabalha a partir desta especificação, não do código do Sam.

## Escopo da v0.1

| Dentro | Fora (roadmap) |
|---|---|
| Biblioteca `jawa-core` com todas as regras e travas | GUI (React + Tauri), prevista para a v0.3 |
| CLI: `jawa medir`, `jawa explicar`, `jawa limpar`, `jawa historico` | Execução com root via `pkexec`, prevista para a v0.2 |
| TUI: `jawa` sem argumentos abre a interface no terminal | Dados de apps removidos (`~/.config/<app>`), porque não há como provar o dono |
| Categorias da pasta pessoal, dos projetos e do Docker | Kernels antigos e `apt autoremove` (nunca) |
| Limpezas de sistema em **modo guiado**: mede e mostra o comando, nunca executa | Flatpak (sem estimativa de tamanho confiável) |
| Somente Linux (x86_64) | macOS, Windows, aarch64 |

Interface, mensagens, subcomandos e README são todos em **PT-BR**. Identificadores de código ficam em inglês.

## Travas de segurança (invariantes)

Toda tarefa do plano cita as travas que implementa pelo número (S1 a S19).

| # | Trava |
|---|---|
| S1 | **Medir nunca apaga.** A medição só lê o disco e roda comandos de leitura (`docker system df`, `git check-ignore`, `snap list`, `journalctl --disk-usage`) |
| S2 | **Só limpa o que mediu.** A limpeza aceita apenas ids do último registro de medição (ledger) do mesmo usuário e da mesma pasta pessoal, com no máximo **30 minutos** de idade. Um id desconhecido aborta tudo antes de qualquer ação |
| S3 | **Nada mudou desde a medição.** A impressão digital do alvo (dispositivo, inode, data de modificação) é conferida de novo antes de agir. Se mudou, o item é pulado com "mudou desde a medição" |
| S4 | **Fronteira.** Os caminhos são resolvidos (pai canônico + nome) e precisam estar **estritamente dentro** das raízes da categoria, nunca na própria raiz e nunca escapando por `..` ou symlink. Há uma lista negra global que vale sempre: `/`, `/etc`, `/usr`, `/var`, `/opt`, `/boot`, a própria pasta pessoal, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.kube`, `~/.docker/config.json`, `~/.local/share/keyrings`, qualquer pasta `.git`, e `~/.config` inteiro (exceto as subpastas de cache listadas na S19) |
| S5 | **Nada versionado.** Dentro de repositórios, só entram pastas com **nomes conhecidos** e que o `git check-ignore` confirma estarem ignoradas |
| S6 | **Nada em uso.** Se algum processo tem `cwd` ou executável dentro do alvo, o item fica bloqueado com o nome e o PID do processo. Os caches de apps também ficam bloqueados enquanto o app correspondente estiver aberto (verificado pelo nome do processo) |
| S7 | **Nada pela metade.** Antes de apagar, todas as entradas precisam pertencer ao usuário atual. Se houver arquivos de outro dono (por exemplo, root, criados por um container), o item fica bloqueado e o Jawa sugere `sudo chown -R "$USER": '<caminho>'`. Nunca sugere `rm` com sudo |
| S8 | **Um sistema de arquivos só.** Medir e apagar nunca atravessam pontos de montagem. Um alvo que é ele mesmo um ponto de montagem é recusado |
| S9 | **O disco do Docker Desktop nunca é apagado enquanto o Docker Desktop está instalado** (`/opt/docker-desktop`). Nesse caso só aparece o comando guiado de recuperação de espaço da documentação oficial |
| S10 | **Volumes do Docker, um por um.** Cada volume vira um item com o nome e o projeto do compose (`com.docker.compose.project`). A remoção usa `docker volume rm <nome>`, nunca `prune -a`. Só entram volumes `dangling` (sem nenhum container, nem parado) |
| S11 | **Níveis de risco.** `Seguro` vem marcado. `Revisar` vem desmarcado e precisa ser escolhido item a item. `Guiado` nunca é executado e só mostra o comando. Itens **irreversíveis** exigem digitar `apagar` na TUI ou passar `--confirmar-irreversivel` na CLI |
| S12 | **Rastro.** Toda ação (feita, pulada ou com falha) vai para `$XDG_STATE_HOME/jawa/historico.jsonl` |
| S13 | **Uma instância por vez.** Um lock exclusivo em `$XDG_STATE_HOME/jawa/jawa.lock` impede medições ou limpezas simultâneas |
| S14 | **Sem rede e sem telemetria.** O único acesso à rede é o que as próprias ferramentas fazem quando o usuário as roda depois |
| S15 | **Nunca como root.** Com `euid == 0`, o Jawa se recusa a iniciar (evita que um `sudo jawa` apague como root) |
| S16 | **Projeto parado de verdade.** Atividade é o mais recente entre: data do último commit no `HEAD`, modificação de `.git/logs/HEAD` (checkout, pull, commit) e modificação de `.git/index` (add, status). O projeto só é "parado" se essa data for mais antiga que `idle_days` (padrão 30) **e** não houver processo rodando dentro dele (S6) |
| S17 | **Artefatos assinados.** Uma pasta de build que contém `*.apk`, `*.aab`, `*.ipa`, `*.keystore`, `*.jks` ou `*.p12` passa de `Seguro` para `Revisar`, com o nome do arquivo na nota |
| S18 | **Node protegido.** As versões do nvm usadas como padrão (seguindo a cadeia de aliases), pedidas por qualquer `.nvmrc` dos projetos ou ativas no `PATH` nunca são oferecidas. Cada item lista os pacotes globais que somem junto |
| S19 | **`~/.config` só por lista.** Ali só entram subpastas de cache conhecidas: `Code/{Cache,CachedData,CachedExtensionVSIXs,Code Cache,GPUCache,logs}`, `Slack/{Cache,Code Cache,GPUCache,logs}` e `discord/{Cache,Code Cache,GPUCache}` |

## Categorias da v0.1

| Id | Título | Risco | Reversibilidade | O que entra (Linux) |
|---|---|---|---|---|
| `npm-cache` | Cache do npm | Seguro | Regenerável | `~/.npm/_cacache`, `~/.npm/_npx` |
| `caches-ferramentas` | Caches de ferramentas | Seguro | Regenerável | Em `$XDG_CACHE_HOME`: `ms-playwright`, `Cypress`, `puppeteer`, `yarn`, `pnpm`, `node-gyp`, `typescript`, `pip`, `prisma`, `go-build`, `thumbnails`. Na pasta pessoal: `.gradle/caches`, `.cargo/registry`. Versões antigas do Claude Code em `~/.local/share/claude/versions` (exceto o alvo de `~/.local/bin/claude`) |
| `caches-apps` | Caches de aplicativos | Seguro (bloqueado com o app aberto) | Regenerável | `$XDG_CACHE_HOME/{google-chrome,chromium,mozilla,spotify}` + as subpastas da S19. Processos vigiados: `chrome`, `chromium`, `firefox`, `code`, `slack`, `spotify`, `Discord` |
| `saidas-build` | Saídas de build | Seguro (Revisar pela S17) | Regenerável | `dist`, `build`, `www`, `coverage`, `.angular/cache`, `.nx/cache` até 3 níveis dentro de cada repo, só se ignorados (S5) |
| `rust-target` | Builds do Rust | Seguro | Regenerável | `target/` ao lado de um `Cargo.toml`, nos repos e nas pastas até 2 níveis abaixo da pessoal; dentro de repo, só se ignorado |
| `node-modules-parados` | Dependências de projetos parados | Revisar | Regenerável | `node_modules` (até 3 níveis) de projetos parados (S16). A nota traz o comando de reinstalação pelo lockfile e um aviso de **registry privado** se o `.npmrc` do projeto tiver `_authToken` ou `@escopo:registry` |
| `nvm-versoes` | Versões antigas do Node (nvm) | Revisar | Regenerável | `$NVM_DIR/versions/node/v*` (padrão `~/.nvm`), menos as protegidas (S18) |
| `docker-imagens` | Docker: imagens e cache de build | Seguro | Regenerável | `docker image prune -a -f`, `docker builder prune -a -f`, com tamanho do `docker system df` |
| `docker-volumes` | Docker: volumes e containers parados | Revisar | **Irreversível** | Um item por volume `dangling` (S10) + um item "containers parados" (`docker container rm <ids>` com os IDs medidos, sem `-f`) |
| `docker-desktop-disco` | Disco virtual do Docker Desktop | Guiado / Revisar | Irreversível | `~/.docker/desktop/vms/0/data/Docker.raw` com tamanho real. Instalado: guiado com `docker run --privileged --pid=host docker/desktop-reclaim-space`. Não instalado: Revisar, apagando `~/.docker/desktop/vms` |
| `downloads` | Downloads grandes e antigos | Revisar | Lixeira | Na pasta XDG de downloads: pacotes (`.deb`, `.rpm`, `.AppImage`, `.iso`, `.img`, `.tar.gz`, `.tgz`, `.tar.xz`, `.zip`) de 10 MB ou mais; qualquer item de 100 MB ou mais; itens de 10 MB ou mais parados há 90 dias. Pula ocultos e downloads em andamento (`.part`, `.crdownload`) |
| `sistema` | Sistema (modo guiado) | Guiado | — | journald acima de 200 MB (`sudo journalctl --vacuum-size=200M`), `.deb` em `/var/cache/apt/archives` (`sudo apt-get clean`), cada revisão `disabled` de snap (`sudo snap remove <nome> --revision=<rev>`), `/var/crash/*.crash` (`sudo rm -f /var/crash/*.crash`) |

Itens com caminho abaixo de **1 MiB** não aparecem. Sem a ferramenta (git, docker, nvm, snap, apt), a categoria explica por que não há o que mostrar.

Cada categoria tem uma explicação com seis campos, exibidos com `jawa explicar <id>` e no painel da TUI: **o que é**, **por que cresce**, **o que acontece ao limpar**, **dá para desfazer?**, **custo para recriar** e **recomendação**.

## Configuração

Fica em `$XDG_CONFIG_HOME/jawa/config.toml`:

```toml
project_roots = ["/home/eu/field"]   # vazio = detectar
idle_days = 30                       # 1..=365
```

Na detecção, valem as pastas até 2 níveis abaixo da pessoal (sem ocultas, `snap` nem a pasta de downloads) que tenham **pelo menos 2 repositórios git como filhos diretos**.

## Avisos cruzados

Na confirmação, conforme a combinação escolhida:

- `npm-cache` + `node-modules-parados`: "As reinstalações vão baixar tudo da internet."
- Qualquer item com registry privado: "Algum projeto usa registry privado: confira se o token ainda vale antes de reinstalar."
- Qualquer item na Lixeira: "O espaço só volta quando você esvaziar a Lixeira."

## Resultado da limpeza

O relatório mostra o espaço **estimado** (soma dos itens) e o espaço **medido** (diferença do espaço livre na pasta pessoal, antes e depois). Se o medido for menor que metade do estimado, mostra: "Parte do espaço pode estar presa em snapshots (Btrfs/Timeshift) ou na Lixeira."
